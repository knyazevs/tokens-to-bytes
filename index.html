Abstract

Может ли языковая модель писать WebAssembly-байткод напрямую, без исходного языка и компилятора? Этот артефакт измеряет цену такого подхода на одном прикладном примере: калькуляторе с фиксированным API из 17 функций и одинаковым поведением.

Сравниваются шесть сборок: байткод, написанный моделью, и реализации на Rust, AssemblyScript, C и C++ — последний в двух вариантах, с оптимизацией по размеру (-Oz) и по скорости (-O3). Для каждой измеряются токены артефакта, корректность на общем наборе тестов, размер модуля и скорость выполнения. Результат: самый маленький модуль в сырых байтах — у AssemblyScript (1164 Б), но после gzip и brotli первым становится ручной байткод (610 и 574 Б). Ручной WAT требует в 1,9–2,5 раза больше токенов, чем исходники на C или C++. По скорости все шесть сборок укладываются в 1,15 раза; в парных замерах ручной модуль уступает C++ -O3 около 3 %, а прочие пары, кроме C++ -Oz/-O3, неразличимы. Компиляторы выигрывают по стоимости авторинга, ручной байткод — по сжатому весу.

Второй проект — JSON-парсер с 27 тестами — проверяет, что происходит с этим балансом при переходе от арифметики к разбору строк. Там ручной байткод уже не выигрывает ни в сырых байтах, ни после сжатия, а разрыв по токенам растёт до 2,3–2,9 раза. Скорость шести сборок остаётся в пределах 1,11 раза.

1 Вопросы

Пять вопросов задают протокол измерений. Первые четыре закрываются на калькуляторе; пятый — повестка следующих проектов.

RQ1 · Цена

Сколько токенов нужно, чтобы получить корректный модуль, и как это соотносится с исходником на высокоуровневом языке?

RQ2 · Валидируемость

Насколько полно поведение покрывается автоматическими тестами и совпадает ли оно между независимыми реализациями?

RQ3 · Вес

Сколько байт занимает модуль до и после gzip/brotli — и проигрывает ли ручной байткод компиляторам?

RQ4 · Производительность

Насколько быстро синтезированный байткод выполняет одинаковую нагрузку по сравнению со сборками из компиляторов?

RQ5 · Масштабирование

Сохраняются ли выводы при переходе от калькулятора к более сложным приложениям — парсерам, регулярным выражениям, интерпретаторам?

Метрика честности

Что именно не измерено: токены генерации и время разработки требуют логирования в момент генерации. В v0.1 они отмечены явно, а не реконструированы задним числом.

2 Установка

Один поведенческий контракт, шесть сборок на пяти языках.

Все модули экспортируют один и тот же набор функций. Внешний код — кнопки калькулятора — не знает, на каком языке написана реализация: он вызывает digit, op, equals и читает display. Состояние ввода, дроби, backspace, смена знака, цепочки операций и повтор = живут внутри модуля.

17 экспортов. Ни один модуль не импортирует ничего из окружения: WebAssembly.Module.imports() пуст для всех сборок. Это делает сравнение чистым — измеряется только код, а не адаптеры.

Что считается «ручным» байткодом. Модуль calc.wasm написан моделью как WAT — без высокоуровневого исходника и компилятора — и собран в байткод через wasm-as. Именно calc.wat (261 строка) служит формой авторинга и источником для подсчёта токенов.

3 Метод

Что и как измеряется — с явными границами применимости.

Метрики

  • Токены артефакта — countTokens (o200k_base) от естественной формы: исходник на языке реализации или WAT для ручного байткода. Это нижняя граница стоимости генерации: модель ещё тратит токены на рассуждение, ошибки и правки.
  • Токены генерации — usage.output_tokens конкретного прогона. В v0.1 не измерялись; протокол для будущих прогонов описан ниже.
  • Тесты — 16 сценариев ввода/арифметики и одна проверка формулы после =. Один и тот же код выполняется в Node и в браузере.
  • ops/sec — вызовы API в секунду на детерминированной нагрузке. Каждая сборка измеряется в отдельном процессе Node: прогрев 750 мс, затем десять окон по 150 мс, шесть таких процессов; медиана по всем 60 замерам. Рядом с медианой публикуются минимум, среднее, максимум и стандартное отклонение — они показывают шум, который медиана скрывает. Для JSON-парсера одна операция — разбор одного документа, поэтому единица в таблице — документы в секунду; протокол и число замеров те же.
  • Размер — байты модуля, gzip уровня 9 и brotli качества 11.

Нагрузка

Нагрузка — 12 последовательностей по 76 вызовов API за проход: цифры, дроби, все четыре операции, повтор =, backspace и смена знака. Последовательности детерминированы и одинаковы для всех сборок; clear() вызывается перед каждой и включается в счётчик.

Окружение

Загрузка окружения…

Почему отдельный процесс на сборку

Первая версия бенчмарка измеряла все сборки подряд в одном процессе Node — и C++ стабильно оказывался вдвое медленнее остальных. Проверка исходников и байткода ничего не объяснила: пересборка с точными флагами дала байт-в-байт тот же модуль, а дизассемблер C++ был даже компактнее C. Причина оказалась в замере, и она двойная.

  • Голодание tier-up. V8 поднимает оптимизацию wasm-модулей по мере прогрева. Когда в одном JS-контексте горячих модулей несколько, бюджеты компиляции делятся, и сборка, измеренная последней, не успевает выйти на оптимизированный код. Если поменять порядок, «медленной» становилась уже другая реализация — ровно наоборот к прежней.
  • Миграция на E-ядра. На гибридных процессорах Windows переносит процесс между P- и E-ядрами. E-ядра здесь в ~2,2 раза медленнее, и уже разогретый процесс может уехать на них посреди замера. Привязка к P-ядрам выравнивает картину.

Поэтому протокол стал таким: builds/bench-one.mjs запускается отдельным процессом на каждую сборку, а в браузере каждая сборка получает собственный Worker. Внутри процесса — прогрев 750 мс, десять окон по 150 мс и медиана; снаружи — шесть повторов, то есть 60 замеров на сборку. Привязка к ядрам записывается в data/calculator.json вместе с методом.

Чему это учит. Разница между «C++ вдвое медленнее» и «C++ в пределах 15 % от лучшего» была целиком методической. Микробенчмарки, где несколько реализаций греются в одном рантайме, систематически занижают результат тем, кто измерен позже.

Парные проверки

Опубликованные 60 замеров отвечают на вопрос «как быстро сборка работает обычно», но не разрешают разницу в 2–3 %. Для таких сравнений использован отдельный эксперимент: 20 блоков, в каждом все сравниваемые сборки запускаются по одному разу в случайном порядке; разница считается внутри блока, интервал — парным бутстрепом по блокам. Это вспомогательная проверка, а не замена основному протоколу, поэтому её числа приведены в тексте, а не в data/calculator.json.

Протокол для токенов генерации

Чтобы измерить реальную стоимость, каждый прогон выполняется в чистой сессии с фиксированным промптом, а из ответа API сохраняются usage.input_tokens, usage.output_tokens, число итераций до зелёных тестов и wall-clock. Результат пишется в data/runs.json. Пока там только схема и null — заполнять задним числом было бы нечестно.

Почему ops/sec — не абсолют. Микробенчмарк измеряет пару «JS-вызов → wasm-функция», поэтому накладные расходы вызова входят в результат. Он сравним между реализациями, но не описывает вычислительную мощность wasm в целом.

Наблюдения

  • Вес. В сырых байтах лидирует AssemblyScript — 1 164 Б; ручной байткод после оптимизации занимает 1 418 Б (+21,8 %). После gzip и brotli порядок меняется: ручной модуль — 610 и 574 Б, AssemblyScript — 616 и 588 Б. Дальше C++ -Oz (1 872 Б) и C (1 935 Б); C++ -O3 заметно тяжелее — 2 437 Б (+30 % к -Oz), Rust — 2 042 Б. После gzip разрыв между двумя вариантами C++ сокращается: 911 и 987 Б (brotli — 822 и 900 Б).
  • Токены. Дешевле всего писать на C (1 209 токенов) и C++ (1 225 — у обоих вариантов один и тот же исходник), дороже — AssemblyScript (1 411) и Rust (1 548). Ручной WAT требует 3 006 токенов — в 1,9–2,5 раза больше лучших компилируемых вариантов. В base64 картина другая: 994 токена у ручного модуля против 1 403 у C++ -Oz и 1 440 у C; дешевле только AssemblyScript (827).
  • Скорость. В изолированных процессах шесть сборок укладываются в 1,15 раза: от 126,7M до 146,3M ops/sec. Внутри одной сборки σ — 1,9–4,4 % от медианы, поэтому одиночный замер не разрешает разницу в единицы процентов. Парные блоки со случайным порядком (20 блоков, по одному замеру на сборку в блоке) дают более узкий ответ: оптимизированный ручной модуль на 2,0 % быстрее прежней ручной версии (16 побед из 20) и на 3,1 % медленнее C++ -O3 (1 победа из 20); бутстреп-интервалы не включают ноль; абсолютные медианы между сессиями смещаются, поэтому сравнение — внутри парных блоков. Остальные пары с участием ручного модуля — в пределах шума. Устойчива и разница между вариантами C++: -O3 даёт около +7 % к -Oz и стоит +30 % байт модуля.
  • Что изменилось в ручном модуле. Прежняя версия была самой маленькой (1 147 Б), но не самой быстрой. Новая убирает вызовы горячих хелперов, заменяет цепочку сравнений оператора на br_table, инлайнит applyOp и сбрасывает состояние лениво. Цена — +23,6 % сырых байт (1 418 против 1 147); выигрыш — +2,0 % скорости. Сжатый размер почти не изменился: gzip 610 против 595 Б, brotli 574 против 567 Б. Поведение сверено дифференциальным фаззером: 500 000 сравнений состояния на случайных последовательностях, расхождений нет.
  • Что было не так с C++. Прежняя цифра «в 2,8 раза медленнее» — артефакт замера, а не свойство кода. После перехода на изолированные процессы C++ перестал быть выбросом; отдельная сборка с -O3 показывает, сколько стоит оптимизация по скорости поверх -Oz.

Вывод. Прямой синтез байткода оправдан, когда важнее сжатый вес и предсказуемость рантайма, а не стоимость разработки. Компиляторы дают более дешёвый авторинг; AssemblyScript даже легче в сырых байтах, но уступает ручному модулю 6–14 Б после gzip/brotli и требует цепочки инструментов.

5 JSON-парсер

Второй проект: рекурсия, UTF-8, escape-последовательности и ошибки с позициями — на том же контракте из шести сборок.

Калькулятор проверяет состояние и арифметику. JSON-парсер добавляет то, чего в нём нет: цикл по входному буферу, рекурсивный спуск, декодирование строк, \u-escape с суррогатными парами, числа с плавающей точкой и точную позицию первой ошибки. Интерфейс остаётся байтовым: страница копирует UTF-8 в память модуля, вызывает json_parse(len) и читает счётчики. Ни одна сборка ничего не импортирует.

Контракт API

json_input_ptr() → i32          // входной буфер, 64 КиБ
json_parse(len) → i32           // 0 — успех, иначе код ошибки
json_error_pos() → i32
json_error_code() → i32
json_root_type() → i32          // 0 null · 1 false · 2 true · 3 number · 4 string · 5 array · 6 object
json_root_number() → f64
json_root_len() → i32
json_root_ptr() → i32
json_nodes() · json_depth() · json_numbers()
json_strings() · json_string_bytes()

27 общих тестов: 13 корректных документов и 14 некорректных. Проверяются коды ошибок и их позиции, поэтому «угадать» ответ нельзя. Счётчики структуры — узлы, глубина, числа, строки и байты декодированных строк — считаются одинаково: контейнер тоже узел, ключи объекта входят в число строк, глубина начинается с единицы. Лимиты — 64 КиБ входа, 4 КиБ корневой строки и глубина 64.

Наблюдения

  • Вес. В сырых байтах лидирует AssemblyScript — 3 190 Б; ручной байткод занимает 3 271 Б (+2,5 %). После gzip и brotli AssemblyScript по-прежнему первый (1 378 и 1 259 Б), ручной модуль — второй (1 385 и 1 268 Б, +0,5 % и +0,7 %). Дальше C (4 137 Б; 1 866 и 1 644 Б), C++ -Oz (4 676 Б; 2 045 и 1 803 Б), Rust (4 699 Б; 2 038 и 1 843 Б) и C++ -O3 (5 701 Б; 2 280 и 2 012 Б). Проигрыш ручного байткода по сырым байтам — 2,5 %, по сжатым — меньше процента.
  • Токены. Дешевле всего писать на C (3 303 токена) и C++ (3 400 — один исходник на два варианта), дороже — AssemblyScript (3 828) и Rust (4 135). Ручной WAT требует 9 556 токенов — в 2,3–2,9 раза больше компилируемых вариантов. В base64 картина иная: 2 524 токена у AssemblyScript, 2 599 у ручного модуля, 3 219 у C, 3 728 и 4 532 у C++ -Oz/-O3.
  • Скорость. Шесть сборок укладываются в 1,11 раза: от 2,6M до 2,9M документов в секунду. Быстрее всех C++ -O3; ручной байткод — последний. Разница -O3 к -Oz — около +8 % при +22 % сырых байт. Парных блоков для JSON не проводилось, поэтому различия меньше 2–3 % здесь не разрешаются.
  • Корректность. Все шесть сборок проходят 27/27 тестов, включая позиции ошибок для 14 некорректных документов. Общий оракул считает структуру по эталонному разбору, поэтому расхождение в счётчиках или позиции сразу видно.
  • Что изменилось относительно калькулятора. Ручной байткод перестал быть самым лёгким: на рекурсивном разборе строк AssemblyScript выигрывает и в сырых байтах, и после сжатия. Разрыв по токенам вырос с 1,9–2,5 до 2,3–2,9 раза, а скорость осталась ровной — 1,11 раза между лучшей и худшей сборкой.

Вывод. Переход от арифметики к разбору строк усиливает главный компромисс: ручной байткод остаётся конкурентоспособным по скорости и почти догоняет лучший сжатый размер, но стоит в 2,3–2,9 раза больше токенов. AssemblyScript на этой задаче — самый дешёвый по авторингу и самый маленький по весу; C++ -O3 — самый быстрый, но самый тяжёлый.

7 Бенчмарк

Та же нагрузка, но исполняется в вашем браузере прямо сейчас.

Кнопка ниже загружает все шесть модулей и выполняет одинаковую нагрузку — 76 вызовов API за проход. Каждая сборка измеряется в своём Worker: прогрев 500 мс, семь раундов по 150 мс; в таблице — медиана и коридор от минимума до максимума. 9 Ограничения

Что может сломать выводы — и что для этого нужно сделать.

  • Два проекта, шесть сборок. Калькулятор — маленькая state machine, JSON-парсер — рекурсивный разбор строк. Оба показывают схожую картину по скорости, но противоположную по весу; переносить числа на regex и интерпретатор байткода без новых измерений всё ещё нельзя. Это и есть RQ5.
  • Токены артефакта — не стоимость генерации. Они не включают рассуждение, отвергнутые варианты и отладку. Реальная цена может быть в разы выше; для её измерения нужен лог usage.output_tokens.
  • WAT — форма авторинга. Ручной модуль написан как WAT и собран wasm-as; 3 006 токенов у калькулятора и 9 556 у JSON-парсера считаются по этой форме. Другая запись (инструкции, base64) дала бы другое число, но не меняет порядок величины.
  • Микробенчмарк. Доминируют накладные расходы вызова JS → wasm. Разница между -Oz и -O3 на таком объёме кода мала и может измениться при другой нагрузке.
  • Одно окружение. Node 24 на одной машине; заголовочное число — медиана по 60 замерам, шум показан минимумом, максимумом и σ. Парные сравнения в тексте используют бутстреп-интервалы, но остаются измерением на одной машине. Браузерный запуск — независимая, но не идентичная проверка.
  • Поведенческие тесты, не формальная верификация. 17 проверок калькулятора и 27 проверок JSON-парсера покрывают заявленное поведение, но не доказывают отсутствие ошибок на всех входах. Fuzzing и сравнение с эталонной моделью — следующий шаг.
  • Разные тулчейны. Компиляторы получают -Oz и wasm-opt; C++ дополнительно собран с -O3 как отдельный артефакт, чтобы отделить размер от скорости. Ручной модуль переписан вручную под скорость — без автоматических оптимизаторов вроде wasm-opt. Это ближе к реальному использованию, но не идеально контролируемый эксперимент.

10 Воспроизведение

Все числа в статье пересчитываются двумя командами на проект.

git clone https://github.com/knyazevs/tokens-to-bytes
cd tokens-to-bytes
npm install

npm run tokens              # data/tokens.json — токены калькулятора
npm run measure             # data/calculator.json — размер, тесты, ops/sec
npm run tokens -- json      # data/tokens-json.json — токены JSON-парсера
npm run measure -- json     # data/json.json — размер, тесты, док./с
npm run build:manual        # calc.wasm из calc.wat через wasm-as
npm run build:json          # шесть сборок JSON-парсера

Замер на гибридном процессоре стоит привязывать к P-ядрам, иначе Windows может перенести процесс на E-ядра посреди прогона: AFFINITY=FFF в окружении и start /affinity FFF для запуска. Привязка попадёт в файл измерений проекта вместе с методом.

Для пересборки wasm из исходников нужны Rust с таргетом wasm32-unknown-unknown, AssemblyScript, clang с wasm-ld, wasm-opt и wasm-as из Binaryen. Точные команды и конфиги лежат в builds/; готовые бинарники уже в репозитории, поэтому для проверки измерений тулчейны не нужны.

tokens-to-bytes/
├─ index.html                 статья
├─ assets/                    стили, скрипты, общие протоколы
├─ data/
│  ├─ projects.json           реестр проектов
│  ├─ calculator.json         измерения калькулятора
│  ├─ json.json               измерения JSON-парсера
│  ├─ tokens.json             токены калькулятора
│  └─ tokens-json.json        токены JSON-парсера
├─ projects/calculator/       демо + шесть wasm + WAT
├─ projects/json/             демо + шесть wasm + WAT
└─ builds/                    исходники, сборка, измерение

Любая сборка запускается в демо отдельно: projects/json/index.html?engine=json-rust.wasm. Страницы бенчмарков: projects/calculator/bench.html и projects/json/bench.html.
