Abstract

Может ли языковая модель писать WebAssembly-байткод напрямую, без исходного языка и компилятора? Этот артефакт измеряет цену такого подхода на одном прикладном примере: калькуляторе с фиксированным API из 17 функций и одинаковым поведением.

Сравниваются шесть сборок: байткод, написанный моделью, и реализации на Rust, AssemblyScript, C и C++ — последний в двух вариантах, с оптимизацией по размеру (-Oz) и по скорости (-O3). Для каждой измеряются токены артефакта, корректность на общем наборе тестов, размер модуля и скорость выполнения. Результат: самый маленький модуль в сырых байтах — у AssemblyScript (1164 Б), но после gzip и brotli первым становится ручной байткод (610 и 574 Б). Ручной WAT требует в 1,9–2,5 раза больше токенов, чем исходники на C или C++. По скорости все шесть сборок укладываются в 1,15 раза; в парных блоках ручной модуль уступает C++ -O3 2,7 %, а разрывы компилированных сборок доходят до 13,3 % у Rust. Компиляторы выигрывают по стоимости авторинга, ручной байткод — по сжатому весу.

Второй проект — JSON-парсер с 27 тестами — проверяет, что происходит с этим балансом при переходе от арифметики к разбору строк. Там ручной байткод уже не выигрывает ни в сырых байтах, ни после сжатия, а разрыв по токенам растёт до 2,3–2,9 раза. Скорость шести сборок остаётся в пределах 1,11 раза; в парных блоках все уступают C++ -O3 — от 6,6 % у C до 9,9 % у ручного модуля.

Третий проект — regex-движок с 61 тестом — добавляет компиляцию шаблона в байткод, бэктрекинг и защиту от катастрофического перебора. Здесь ручной WAT снова самый дорогой по токенам — в 2,3–2,6 раза дороже компилируемых вариантов, — а разброс скорости между шестью сборками составляет 1,22 раза: впервые заметно медленнее становится не только ручной модуль (10,3 %), но и AssemblyScript (17,4 %). C и C++ -Oz в парных блоках уступают C++ -O3 меньше 1,5 %.

Четвёртый проект — стековая VM с 52 тестами — переносит интерпретацию внутрь wasm: 27 команд, кадры вызовов и стек значений. Ручной WAT впервые выигрывает и gzip, и brotli (782 Б), но платит 2,8–3,6 раза больше токенов и 48 % сырых байт; по скорости он даже немного обгоняет C++ -O3 — на 2,3 % в парных блоках. Разброс 2,60 раза целиком создаёт AssemblyScript: он работает в 2,6 раза медленнее лидера.

Ключевые слова: WebAssembly; генерация кода языковыми моделями; артефакт; корректность; размер модуля; производительность; сжатие; байткод.

Abstract
EN

Can a language model write WebAssembly bytecode directly, without a high-level language and a compiler? This artifact studies four programs — a calculator, a JSON parser, a regular-expression engine and a stack virtual machine — each implementing a fixed API in six builds: hand-written WAT, Rust, AssemblyScript, C, and C++ compiled twice (-Oz and -O3). For every build we measure artifact tokens, behavioural correctness on a shared suite of 157 tests, module size (raw, gzip -9, brotli q11), and throughput on a deterministic workload.

Across the series the hand-written module costs 1.9–3.6× more tokens than the cheapest compiled source, yet it remains competitive after compression: it has the smallest compressed module in two of the four projects and stays within 7 % of the best gzip size in the others. Throughput differences among compiled builds are small but project-dependent. Paired randomized blocks resolve contrasts down to a few percentage points: on the stack VM the hand-written module is 2.3 % faster than C++ -O3, whereas on the calculator Rust trails the leader by 13 % and AssemblyScript is 2.6× slower than the VM leader. We report effect sizes with bootstrap intervals, discuss threats to validity, and publish the complete artifact: sources, binaries, benchmarks, measurements and analysis scripts.

Keywords: WebAssembly; large language models; code generation; artifact evaluation; performance measurement; compression; bytecode.

1 Вопросы

Пять вопросов задают протокол измерений. RQ1–RQ4 проверяются на каждом проекте, RQ5 — сравнением четырёх проектов между собой.

RQ1 · Цена

Сколько токенов нужно, чтобы получить корректный модуль, и как это соотносится с исходником на высокоуровневом языке?

RQ2 · Валидируемость

Насколько полно поведение покрывается автоматическими тестами и совпадает ли оно между независимыми реализациями?

RQ3 · Вес

Сколько байт занимает модуль до и после gzip/brotli — и проигрывает ли ручной байткод компиляторам?

RQ4 · Производительность

Насколько быстро синтезированный байткод выполняет одинаковую нагрузку по сравнению со сборками из компиляторов?

RQ5 · Масштабирование

Сохраняются ли выводы при переходе от калькулятора к более сложным приложениям — парсерам, регулярным выражениям, интерпретаторам?

Метрика честности

Что именно не измерено: токены генерации и время разработки требуют логирования в момент генерации. В этой версии они отмечены явно, а не реконструированы задним числом.

Контекст и предыдущие работы

Генерация кода по естественному описанию обычно оценивается на функциональных задачах: HumanEval и MBPP проверяют, проходит ли предложенная функция набор юнит-тестов [3, 4]. Такая метрика отвечает на вопрос о правильности, но не о том, во что обходится артефакт, сколько он весит после компиляции и как быстро исполняется. Более поздние модели для кода сообщают о качестве на тех же или близких наборах [5, 6].

WebAssembly спроектирован как компактный, переносимый и безопасный формат с валидацией и структурированным управлением [1, 2]. Компиляторы из Rust, C и C++ дают предсказуемый, но не обязательно минимальный модуль: размер и скорость зависят от флагов и оптимизатора. Прямое написание байткода убирает компилятор из цепочки, но перекладывает на автора валидацию, управление стеком и обработку ошибок.

Насколько нам известно, систематических измерений этого компромисса на одном контракте в нескольких прикладных программах мало. Вклад работы — артефакт и протокол: четыре программы, шесть реализаций, общий набор из 157 тестов, одинаковые измерения токенов, веса и скорости, дифференциальный фаззер для VM и парные блоки для сравнения производительности.

2 Установка

Один поведенческий контракт, шесть сборок на пяти языках.

Все модули экспортируют один и тот же набор функций. Внешний код — кнопки калькулятора — не знает, на каком языке написана реализация: он вызывает digit, op, equals и читает display. Состояние ввода, дроби, backspace, смена знака, цепочки операций и повтор = живут внутри модуля.

17 экспортов. Ни один модуль не импортирует ничего из окружения: WebAssembly.Module.imports() пуст для всех сборок. Это делает сравнение чистым — измеряется только код, а не адаптеры.

3 Метод

Что и как измеряется — с явными границами применимости.

Метрики

  • Токены артефакта — countTokens (o200k_base) от естественной формы: исходник на языке реализации или WAT для ручного байткода. Это нижняя граница стоимости генерации: модель ещё тратит токены на рассуждение, ошибки и правки.
  • Токены генерации — usage.output_tokens конкретного прогона. В этой версии не измерялись; протокол для будущих прогонов описан ниже.
  • Тесты — 16 сценариев ввода/арифметики и одна проверка формулы после =. Один и тот же код выполняется в Node и в браузере.
  • ops/sec — вызовы API в секунду на детерминированной нагрузке. Каждая сборка измеряется в отдельном процессе Node: прогрев 750 мс, затем десять окон по 150 мс, шесть таких процессов; медиана по всем 60 замерам. Рядом с медианой публикуются минимум, среднее, максимум и стандартное отклонение — они показывают шум, который медиана скрывает. Для JSON-парсера одна операция — разбор одного документа, поэтому единица в таблице — документы в секунду; протокол и число замеров те же.
  • Размер — байты модуля, gzip уровня 9 и brotli качества 11.

Нагрузка

Нагрузка — 12 последовательностей по 76 вызовов API за проход: цифры, дроби, все четыре операции, повтор =, backspace и смена знака. Последовательности детерминированы и одинаковы для всех сборок; clear() вызывается перед каждой и включается в счётчик.

Окружение

Загрузка окружения…

Почему отдельный процесс на сборку

Первая версия бенчмарка измеряла все сборки подряд в одном процессе Node — и C++ стабильно оказывался вдвое медленнее остальных. Проверка исходников и байткода ничего не объяснила: пересборка с точными флагами дала байт-в-байт тот же модуль, а дизассемблер C++ был даже компактнее C. Причина оказалась в замере, и она двойная.

  • Голодание tier-up. V8 поднимает оптимизацию wasm-модулей по мере прогрева. Когда в одном JS-контексте горячих модулей несколько, бюджеты компиляции делятся, и сборка, измеренная последней, не успевает выйти на оптимизированный код. Если поменять порядок, «медленной» становилась уже другая реализация — ровно наоборот к прежней.
  • Миграция на E-ядра. На гибридных процессорах Windows переносит процесс между P- и E-ядрами. E-ядра здесь в ~2,2 раза медленнее, и уже разогретый процесс может уехать на них посреди замера. Привязка к P-ядрам выравнивает картину.

Поэтому протокол стал таким: builds/bench-one.mjs запускается отдельным процессом на каждую сборку, а в браузере каждая сборка получает собственный Worker. Внутри процесса — прогрев 750 мс, десять окон по 150 мс и медиана; снаружи — шесть повторов, то есть 60 замеров на сборку. Привязка к ядрам записывается в data/calculator.json вместе с методом.

Чему это учит. Разница между «C++ вдвое медленнее» и «C++ в пределах 15 % от лучшего» была целиком методической. Микробенчмарки, где несколько реализаций греются в одном рантайме, систематически занижают результат тем, кто измерен позже.

Парные проверки

Опубликованные 60 замеров отвечают на вопрос «как быстро сборка работает обычно», но не разрешают разницу в 2–3 %: абсолютные медианы между сессиями смещаются сильнее. Для таких сравнений проведён отдельный эксперимент. В каждом блоке все шесть сборок запускаются по одному разу в случайном порядке, каждая — в отдельном процессе с теми же прогревом и окнами. Отношение считается внутри блока как «сборка / C++ -O3», поэтому медленный дрейф машины сокращается; медиана отношения сопровождается 95 % интервалом из 10 000 бутстреп-пересэмплирований блоков. Калькулятор измерен на 20 блоках, JSON, regex и VM — на 12; порядок внутри блока перемешан генератором с seed 20261119. Это вспомогательная проверка, а не замена основному протоколу: её данные лежат отдельно, в data/paired-<slug>.json, и пересчитываются командой node builds/paired.mjs <slug> <блоки>.

Протокол для токенов генерации

Чтобы измерить реальную стоимость, каждый прогон выполняется в чистой сессии с фиксированным промптом, а из ответа API сохраняются usage.input_tokens, usage.output_tokens, число итераций до зелёных тестов и wall-clock. Результат пишется в data/runs.json. Пока там только схема и null — заполнять задним числом было бы нечестно.

Почему ops/sec — не абсолют. Микробенчмарк измеряет пару «JS-вызов → wasm-функция», поэтому накладные расходы вызова входят в результат. Он сравним между реализациями, но не описывает вычислительную мощность wasm в целом.

Наблюдения

  • Вес. В сырых байтах лидирует AssemblyScript — 1 164 Б; ручной байткод после оптимизации занимает 1 418 Б (+21,8 %). После gzip и brotli порядок меняется: ручной модуль — 610 и 574 Б, AssemblyScript — 616 и 588 Б. Дальше C++ -Oz (1 872 Б) и C (1 935 Б); C++ -O3 заметно тяжелее — 2 437 Б (+30 % к -Oz), Rust — 2 042 Б. После gzip разрыв между двумя вариантами C++ сокращается: 911 и 987 Б (brotli — 822 и 900 Б).
  • Токены. Дешевле всего писать на C (1 209 токенов) и C++ (1 225 — у обоих вариантов один и тот же исходник), дороже — AssemblyScript (1 411) и Rust (1 548). Ручной WAT требует 3 006 токенов — в 1,9–2,5 раза больше лучших компилируемых вариантов. В base64 картина другая: 994 токена у ручного модуля против 1 403 у C++ -Oz и 1 440 у C; дешевле только AssemblyScript (827).
  • Скорость. В изолированных процессах шесть сборок укладываются в 1,15 раза: от 126,7M до 146,3M ops/sec. Внутри одной сборки σ — 1,9–4,4 % от медианы, поэтому одиночный замер не разрешает разницу в единицы процентов. Парные блоки со случайным порядком (20 блоков, по одному замеру на сборку в блоке, seed 20261119) дают более узкий ответ: ручной модуль уступает C++ -O3 2,7 % (95 % ДИ −3,5…−2,3; 1 победа из 20), AssemblyScript — 4,6 %, C++ -Oz — 6,7 %, C — 9,4 %, Rust — 13,3 %; ни один интервал не включает ноль. Абсолютные медианы между сессиями смещаются, поэтому сравнение — внутри парных блоков. Устойчива и разница между вариантами C++: -O3 даёт около +7 % к -Oz и стоит +30 % байт модуля.
  • Что изменилось в ручном модуле. Прежняя версия была самой маленькой (1 147 Б), но не самой быстрой. Новая убирает вызовы горячих хелперов, заменяет цепочку сравнений оператора на br_table, инлайнит applyOp и сбрасывает состояние лениво. Цена — +23,6 % сырых байт (1 418 против 1 147); сжатый размер почти не изменился: gzip 610 против 595 Б, brotli 574 против 567 Б. Ускорения относительно прежней версии парные блоки не подтверждают: она измерялась в другой сессии, а межсессионные медианы смещаются сильнее 2 %. Зато новый модуль стабильно держится в 2,7 % от C++ -O3 и обгоняет C и Rust. Поведение сверено дифференциальным фаззером: 500 000 сравнений состояния на случайных последовательностях, расхождений нет.
  • Что было не так с C++. Прежняя цифра «в 2,8 раза медленнее» — артефакт замера, а не свойство кода. После перехода на изолированные процессы C++ перестал быть выбросом; отдельная сборка с -O3 показывает, сколько стоит оптимизация по скорости поверх -Oz.

Вывод. Прямой синтез байткода оправдан, когда важнее сжатый вес и предсказуемость рантайма, а не стоимость разработки. Компиляторы дают более дешёвый авторинг; AssemblyScript даже легче в сырых байтах, но уступает ручному модулю 6–14 Б после gzip/brotli и требует цепочки инструментов.

Парные блоки

Обычные 60 замеров отвечают на вопрос «как быстро сборка работает обычно», но не разрешают разницу в 2–3 %: между сессиями абсолютные медианы смещаются сильнее. Для таких сравнений проведён отдельный эксперимент. В каждом блоке все шесть сборок запускаются по одному разу в случайном порядке, каждая — в своём процессе; отношение считается внутри блока, поэтому дрейф машины попадает в блок, а не в конкретную реализацию. Второй проект: рекурсия, UTF-8, escape-последовательности и ошибки с позициями — на том же контракте из шести сборок.

6 Regex-движок

Третий проект: шаблон компилируется в байткод, поиск идёт бэктрекингом, а лимит шагов превращает катастрофический перебор в ошибку.

JSON-парсер добавил цикл и рекурсию, но остался детерминированным: один проход по входу. Regex-движок вводит вторую фазу. Сначала re_compile(len) разбирает шаблон и строит программу из восьми инструкций — CHAR, ANY, CLASS, BOL, EOL, JMP, SPLIT, MATCH. Потом каждый re_match(len) исполняет её с явным стеком возвратов: жадные квантификаторы и альтернатива оставляют точки отката, а якоря и классы проверяются на месте. Шаблон и текст лежат в памяти модуля по адресам re_pattern_ptr() и re_text_ptr(); импортов нет.

Поддерживается подмножество без флагов и захватов: литералы, . (кроме перевода строки), классы с диапазонами и \d \w \s, якоря, группы, альтернатива и жадные * + ?. Поиск неякорный — движок пробует каждую стартовую позицию, поэтому ^ и $ остаются явными. Два лимита задают контракт: 1 000 000 шагов VM и стек бэктрекинга на 8 192 точки. Шаблон (a+)+b на сорока a не зависает, а возвращает ошибку 8.

Контракт API

re_pattern_ptr() → i32         // буфер шаблона, 4 КиБ
re_text_ptr() → i32            // буфер текста, 8 КиБ
re_compile(len) → i32          // 0 — успех, иначе код ошибки
re_match(len) → i32            // 1 — совпадение, 0 — нет, −1 — ошибка
re_error() · re_error_pos()    // код и байтовая позиция
re_steps()                     // шагов VM в последнем поиске

61 общий тест: 39 пар «шаблон + текст» с ожидаемым ответом, 18 некорректных шаблонов с кодом и позицией ошибки и 4 проверки контракта — поиск до компиляции, переполнение буфера шаблона, переполнение буфера текста и лимит шагов на катастрофическом шаблоне. Позиции ошибок делают тесты проверкой парсера, а не угадыванием ответа. Лимиты: PATTERN_CAP 4 096 Б, TEXT_CAP 8 192 Б, программа 2 048 инструкций, 64 класса, 8 192 точки отката.

7 Стековая VM

Четвёртый проект: интерпретатор собственного байткода с кадрами вызовов — цикл, ветвления и рекурсия внутри wasm.

Regex-движок исполнял программу, которую строил сам, но не давал программе управлять собой. Стековая VM меняет роли: байткод приходит снаружи, и модуль обязан его проверить, исполнить и корректно упасть. Формат — 4 байта на инструкцию [op, x, y, z]: PUSH несёт знаковое 24-битное число, переходы — адрес инструкции, LOADL/STOREL — индекс локала. Двадцать семь команд: арифметика, сравнения, логика, стековые операции, переходы, вызовы и HALT. Памяти данных и плавающих чисел нет — только i32.

Исполнение — цикл с pc, общим стеком значений на 1 024 элемента и кадрами по 8 локалов. CALL кладёт адрес возврата в новый кадр и обнуляет его локалы, RET возвращается назад; глубина ограничена 128 кадрами. Ошибки делятся на два класса. Неизвестный опкод, адрес перехода за программу, локал вне 0…7, пустая программа и длина больше 4 096 инструкций ловятся на vm_load — такой байткод не исполняется вообще. Пустой стек, переполнение стека и кадров, деление на ноль, RET без CALL и лимит шагов возникают в vm_run, и vm_pc() указывает на виновную инструкцию.

Отдельная тонкость — INT_MIN / −1: в wasm инструкция div_s на этой паре ловит ловушку, поэтому все шесть реализаций насыщают результат до INT_MIN, а не падают. Так же согласованы DIV и MOD на нуле: это ошибка 5, а не исключение. Ассемблер общий для тестов, нагрузки, фаззера и демо-страницы и в измеряемую операцию не входит.

Контракт API

vm_code_ptr() → i32            // буфер программы, 4096 инструкций × 4 Б
vm_load(n) → i32               // 0 — принята, иначе код ошибки
vm_run(limit) → i32            // 0 — HALT, −1 — ошибка; limit ≤ 0 → 1 000 000 шагов
vm_result() · vm_depth()       // вершина и глубина стека значений
vm_error() · vm_pc() · vm_steps()

52 общих теста: 8 проверок контракта, 31 программа с ожидаемым результатом и 13 некорректных программ с кодом ошибки и pc. Проверки контракта включают запуск до загрузки, пустую программу, программу длиннее буфера, лимит шагов по умолчанию и явный, повторный запуск и перезагрузку после ошибки. Сверх тестов работает дифференциальный фаззер: 60 000 случайных программ (два сида по 30 000) сравнили с эталонной моделью на JavaScript код возврата, ошибку, pc, шаги, глубину и вершину стека. Фаззер нашёл реальное расхождение — ручная сборка снимала операнды деления после проверки на ноль, и глубина стека при ошибке отличалась от C-референса; после исправления все шесть сборок совпали.

AssemblyScript, самый экономный по авторингу и весу, окончательно стал самым медленным: на интерпретаторе с явным стеком и кадрами его сгенерированный код платит за каждую загрузку и сохранение. Это меняет практический вывод: «дешёвый авторский вариант» и «маленький модуль» перестают быть одним и тем же выбором.

Вывод. Стековая VM — проект, где ручной байткод впервые побеждает по сжатому весу и не проигрывает по скорости, но платит максимальные 2,8–3,6 раза токенов и +48 % сырых байт. Компиляторы остаются дешевле в авторинге, а разброс скорости между ними и ручной сборкой исчезает, как только из сравнения убирают AssemblyScript.

10 Проекты

Артефакт спроектирован как серия: калькулятор, JSON-парсер, regex-движок и стековая VM измерены по одному протоколу и собраны в шесть реализаций каждый.

Загрузка реестра…

Каждый проект получает каталог projects/<slug>/, свой реестр реализаций и файл измерений. Статья подхватывает проект из data/projects.json и добавляет карточку в этот раздел. Калькулятор проверяет вызовы и state machine; JSON-парсер добавляет разбор строк, рекурсию и позиции ошибок; regex-движок — компиляцию в байткод, бэктрекинг и лимит шагов; стековая VM — интерпретацию с циклом, ветвлениями, кадрами и стеком вызовов. Все четыре проекта проходят один и тот же цикл: общий контракт API, общие тесты, шесть сборок, замер размера, токенов и скорости.

11 Ограничения

Что может сломать выводы — и что для этого нужно сделать.

  • Четыре проекта, шесть сборок. Калькулятор — маленькая state machine, JSON-парсер — рекурсивный разбор строк, regex-движок — компиляция шаблона и бэктрекинг, стековая VM — интерпретатор байткода с кадрами. Картина по весу меняется от проекта к проекту: ручной WAT дороже всех по сырым байтам, но в VM впервые выигрывает gzip и brotli. Скорость компилированных сборок устойчиво близка, а AssemblyScript в VM заметно отстаёт. Переносить эти числа на произвольную wasm-программу всё ещё нельзя. Это и есть RQ5.
  • Токены артефакта — не стоимость генерации. Они не включают рассуждение, отвергнутые варианты и отладку. Реальная цена может быть в разы выше; для её измерения нужен лог usage.output_tokens.
  • WAT — форма авторинга. Ручной модуль написан как WAT и собран wasm-as; 3 006 токенов у калькулятора, 9 556 у JSON-парсера, 10 727 у regex-движка и 7 948 у стековой VM считаются по этой форме. Другая запись (инструкции, base64) дала бы другое число, но не меняет порядок величины.
  • Микробенчмарк. Доминируют накладные расходы вызова JS → wasm. Разница между -Oz и -O3 на таком объёме кода мала и может измениться при другой нагрузке.
  • Одно окружение. Node 24 на одной машине; заголовочное число — медиана по 60 замерам, шум показан минимумом, максимумом и σ. Парные сравнения в тексте используют бутстреп-интервалы, но остаются измерением на одной машине. Браузерный запуск — независимая, но не идентичная проверка.
  • Поведенческие тесты, не формальная верификация. 17 проверок калькулятора, 27 проверок JSON-парсера, 61 проверка regex-движка и 52 проверки стековой VM покрывают заявленное поведение, но не доказывают отсутствие ошибок на всех входах. Для VM сверх тестов прогнано 60 000 случайных программ против эталонной модели; калькулятор, JSON-парсер и regex-движок такого дифференциального фаззинга пока не проходили.
  • Разные тулчейны. Компиляторы получают -Oz и wasm-opt; C++ дополнительно собран с -O3 как отдельный артефакт, чтобы отделить размер от скорости. Ручной модуль переписан вручную под скорость — без автоматических оптимизаторов вроде wasm-opt. Это ближе к реальному использованию, но не идеально контролируемый эксперимент.

12 Заключение

Прямой синтез байткода выигрывает в узкой нише и проигрывает как универсальная замена компилятору.

Четыре проекта — калькулятор, JSON-парсер, regex-движок и стековая VM — дают согласованную картину. Ручной WAT во всех четырёх дороже по токенам: от 1,9–2,5 раза на калькуляторе до 2,8–3,6 раза на VM. Но после сжатия он остаётся конкурентоспособным: в калькуляторе и VM у него лучший gzip и brotli, в JSON-парсере и regex-движке он уступает лучшему сжатому размеру несколько процентов, а не разы. Сырые байты — худшая метрика для ручного модуля: оптимизатор компилятора даёт более плотную запись, но менее предсказуемую после сжатия.

По скорости компилированные сборки обычно близки, а направление разрыва зависит от проекта. Изоляция процессов убрала главный артефакт первых измерений — мнимую двукратную медленность C++; парные блоки показали, что оставшиеся различия лежат в диапазоне от долей процента до 13 % и разрешаются только внутри блока. На стековой VM ручной модуль даже обгоняет C++ -O3 на 2,3 %; исключение в другую сторону — AssemblyScript на той же VM, который в 2,6 раза медленнее лидера.

Корректность обеспечивается не размером модуля, а контрактом: 157 поведенческих тестов проходят все шесть сборок каждого проекта, а дифференциальный фаззер VM на 60 000 случайных программ нашёл реальное расхождение в ручной сборке — порядок снятия операндов при ошибке DIV/MOD. Это аргумент в пользу того, что прямой синтез байткода должен сопровождаться независимой эталонной моделью, а не только набором примеров.

Практический вывод: писать wasm напрямую имеет смысл для небольших модулей с фиксированным API, где важны сжатый вес, отсутствие цепочки инструментов и предсказуемый рантайм. Для больших программ компиляторы выигрывают по стоимости авторинга, поддержке и скорости разработки. Следующие шаги — измерить токены генерации и время до зелёных тестов, добавить программы с данными и циклами, проверить другие движки wasm и архитектуры, а также расширить дифференциальное тестирование на JSON-парсер и regex-движок.

Ограничения серии перечислены в разделе 11; там же — что именно не измерено и почему.

13 Воспроизведение

Все числа в статье пересчитываются двумя командами на проект; парные блоки — отдельной командой.

git clone https://github.com/knyazevs/tokens-to-bytes
cd tokens-to-bytes
npm install

npm run tokens              # data/tokens.json — токены калькулятора
npm run measure             # data/calculator.json — размер, тесты, ops/sec
npm run tokens -- json      # data/tokens-json.json — токены JSON-парсера
npm run measure -- json     # data/json.json — размер, тесты, док./с
npm run tokens -- regex     # data/tokens-regex.json — токены regex-движка
npm run measure -- regex    # data/regex.json — размер, тесты, поиски/с
npm run tokens -- vm        # data/tokens-vm.json — токены стековой VM
npm run measure -- vm       # data/vm.json — размер, тесты, прогоны/с
npm run build:manual        # calc.wasm из calc.wat через wasm-as
npm run build:json          # шесть сборок JSON-парсера
npm run build:regex         # шесть сборок regex-движка
npm run build:vm            # шесть сборок стековой VM
node builds/paired.mjs calculator 20
node builds/paired.mjs json 12
node builds/paired.mjs regex 12
node builds/paired.mjs vm 12

Замер на гибридном процессоре стоит привязывать к P-ядрам, иначе Windows может перенести процесс на E-ядра посреди прогона: AFFINITY=FFF в окружении и start /affinity FFF для запуска. Привязка попадёт в файл измерений проекта вместе с методом.

Для пересборки wasm из исходников нужны Rust с таргетом wasm32-unknown-unknown, AssemblyScript, clang с wasm-ld, wasm-opt и wasm-as из Binaryen. Точные команды и конфиги лежат в builds/; готовые бинарники уже в репозитории, поэтому для проверки измерений тулчейны не нужны.
