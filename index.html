Abstract

Может ли языковая модель писать WebAssembly-байткод напрямую, без исходного языка и компилятора? Этот артефакт измеряет цену такого подхода на одном прикладном примере: калькуляторе с фиксированным API из 17 функций и одинаковым поведением.

Сравниваются пять реализаций: байткод, написанный моделью, и сборки из Rust, AssemblyScript, C и C++. Для каждой измеряются токены артефакта, корректность на общем наборе тестов, размер модуля и скорость выполнения. Предварительный результат: ручной байткод даёт самый маленький модуль (1147 Б) и самую высокую скорость в Node-бенчмарке, но требует в 2,3–2,9 раза больше токенов, чем исходники на C или C++. Компиляторы выигрывают по стоимости авторинга, а не по весу.

1 Вопросы

Пять вопросов задают протокол измерений. Первые четыре закрываются на калькуляторе; пятый — повестка следующих проектов.

RQ1 · Цена

Сколько токенов нужно, чтобы получить корректный модуль, и как это соотносится с исходником на высокоуровневом языке?

RQ2 · Валидируемость

Насколько полно поведение покрывается автоматическими тестами и совпадает ли оно между независимыми реализациями?

RQ3 · Вес

Сколько байт занимает модуль до и после gzip/brotli — и проигрывает ли ручной байткод компиляторам?

RQ4 · Производительность

Насколько быстро синтезированный байткод выполняет одинаковую нагрузку по сравнению со сборками из компиляторов?

RQ5 · Масштабирование

Сохраняются ли выводы при переходе от калькулятора к более сложным приложениям — парсерам, регулярным выражениям, интерпретаторам?

Метрика честности

Что именно не измерено: токены генерации и время разработки требуют логирования в момент генерации. В v0.1 они отмечены явно, а не реконструированы задним числом.

2 Установка

Один поведенческий контракт, пять путей к его реализации.

Все модули экспортируют один и тот же набор функций. Внешний код — кнопки калькулятора — не знает, на каком языке написана реализация: он вызывает digit, op, equals и читает display. Состояние ввода, дроби, backspace, смена знака, цепочки операций и повтор = живут внутри модуля.

// коды операций: 1 = +   2 = −   3 = ×   4 = ÷

17 экспортов. Ни один модуль не импортирует ничего из окружения: WebAssembly.Module.imports() пуст для всех пяти сборок. Это делает сравнение чистым — измеряется только код, а не адаптеры.

Что считается «ручным» байткодом. Модуль calc.wasm написан моделью как байткод, без высокоуровневого исходника. Для токенизации и чтения он представлен в канонической текстовой форме WAT (calc.wat, 612 строк) — это дизассемблер, а не обязательно та форма, в которой модель его порождала.

3 Метод

Что и как измеряется — с явными границами применимости.

Метрики

  • Токены артефакта — countTokens (o200k_base) от естественной формы: исходник на языке реализации или WAT для ручного байткода. Это нижняя граница стоимости генерации: модель ещё тратит токены на рассуждение, ошибки и правки.
  • Токены генерации — usage.output_tokens конкретного прогона. В v0.1 не измерялись; протокол для будущих прогонов описан ниже.
  • Тесты — 16 сценариев ввода/арифметики и одна проверка формулы после =. Один и тот же код выполняется в Node и в браузере.
  • ops/sec — вызовы API в секунду на детерминированной нагрузке. Пять раундов по 120 мс, медиана; перед этим — прогрев 60 мс.
  • Размер — байты модуля, gzip уровня 9 и brotli качества 11.

Нагрузка

Нагрузка — 12 последовательностей по 76 вызовов API за проход: цифры, дроби, все четыре операции, повтор =, backspace и смена знака. Последовательности детерминированы и одинаковы для всех сборок; clear() вызывается перед каждой и включается в счётчик.

Окружение

Загрузка окружения…

Протокол для токенов генерации

Чтобы измерить реальную стоимость, каждый прогон выполняется в чистой сессии с фиксированным промптом, а из ответа API сохраняются usage.input_tokens, usage.output_tokens, число итераций до зелёных тестов и wall-clock. Результат пишется в data/runs.json. Пока там только схема и null — заполнять задним числом было бы нечестно.

Почему ops/sec — не абсолют. Микробенчмарк измеряет пару «JS-вызов → wasm-функция», поэтому накладные расходы вызова входят в результат. Он сравним между реализациями, но не описывает вычислительную мощность wasm в целом.

Наблюдения

  • Вес. Ручной байткод — 1 147 Б; AssemblyScript почти догоняет (1 164 Б, +1,5 %). C++ и C — 1 872 и 1 935 Б, Rust — 2 042 Б. После gzip порядок сохраняется: 595 / 616 / 911 / 944 / 914 Б.
  • Токены. Дешевле всего писать на C (1 209 токенов) и C++ (1 225), дороже — Rust (1 548) и AssemblyScript (1 411). Ручной WAT требует 3 499 токенов — в 2,3–2,9 раза больше лучших компилируемых вариантов.
  • Скорость. В Node ручной байткод быстрее Rust, AssemblyScript и C примерно в 1,4 раза; C++ отстаёт сильнее — ручной модуль быстрее его в 2,8 раза. Разрыв на таких функциях чувствителен к инлайнингу: у C-сборки op и equals заметно быстрее, чем у Rust и C++ при идентичной логике.

Вывод. Прямой синтез байткода оправдан, когда важнее вес и предсказуемость рантайма, а не стоимость разработки. Компиляторы дают более дешёвый авторинг и почти тот же вес (AssemblyScript — +1,5 %), но требуют цепочки инструментов.

5 Демо

Один интерфейс, пять движков. Переключение не меняет ни одной строки UI-кода.

projects/calculator/index.html

Интерфейс калькулятора не знает о языках: он вызывает экспорты, а ?engine= указывает, какой модуль загрузить. Это и есть практическая проверка контракта — если сборка ведёт себя иначе, её видно руками за пару нажатий.

7 Проекты

Артефакт спроектирован как серия: калькулятор — первая, самая простая точка.

Загрузка реестра…

Каждый проект получает каталог projects/<slug>/, свой реестр реализаций и файл измерений. Статья подхватывает проект из data/projects.json и добавляет строку в таблицу и карточку в этот раздел. Следующие приложения добавят то, чего нет в калькуляторе: парсинг строк, регулярные выражения и интерпретацию байткода — там вес и корректность важнее, чем в арифметике.

8 Ограничения

Что может сломать выводы — и что для этого нужно сделать.

  • Один проект, пять реализаций. Калькулятор — маленькая state machine. Переносить числа на парсеры и интерпретаторы без новых измерений нельзя; это и есть RQ5.
  • Токены артефакта — не стоимость генерации. Они не включают рассуждение, отвергнутые варианты и отладку. Реальная цена может быть в разы выше; для её измерения нужен лог usage.output_tokens.
  • WAT — дизассемблер. Ручной байткод мог порождаться не как WAT, а как последовательность инструкций или base64. Тогда 3 499 токенов — верхняя оценка, а не точное значение.
  • Микробенчмарк. Доминируют накладные расходы вызова JS → wasm. Различия в инлайнинге (C++ против C) могут переворачивать порядок при другой нагрузке.
  • Одно окружение. Node 24 на одной машине, один прогон, без доверительных интервалов и статистических тестов. Браузерный запуск — независимая, но не идентичная проверка.
  • Поведенческие тесты, не формальная верификация. 17 проверок покрывают заявленное поведение, но не доказывают отсутствие ошибок на всех входах. Fuzzing и сравнение с эталонной моделью — следующий шаг.
  • Разные тулчейны. Компиляторы получают -Oz и wasm-opt; ручной модуль не оптимизировался постфактум. Это ближе к реальному использованию, но не идеально контролируемый эксперимент.

9 Воспроизведение

Все числа в статье пересчитываются двумя командами.

git clone https://github.com/knyazevs/tokens-to-bytes
cd tokens-to-bytes
npm install

npm run tokens    # data/tokens.json  — токены артефактов
npm run measure   # data/calculator.json — размер, тесты, ops/sec

Для пересборки wasm из исходников нужны Rust с таргетом wasm32-unknown-unknown, AssemblyScript, clang с wasm-ld и wasm-opt. Точные команды и конфиги лежат в builds/; готовые бинарники уже в репозитории, поэтому для проверки измерений тулчейны не нужны.

tokens-to-bytes/
├─ index.html                 статья
├─ assets/                    стили, скрипты, общий протокол
├─ data/
│  ├─ projects.json           реестр проектов
│  ├─ calculator.json         измерения калькулятора
│  └─ tokens.json             токены артефактов
├─ projects/calculator/       демо + пять wasm + WAT
└─ builds/                    исходники, сборка, измерение

Любая сборка запускается в демо отдельно: projects/calculator/index.html?engine=calc-rust.wasm. Страница бенчмарка проекта: projects/calculator/bench.html.
