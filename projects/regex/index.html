Что здесь происходит

Страница копирует UTF-8 шаблон в память модуля по адресу re_pattern_ptr() и вызывает re_compile(len). Разбор шаблона, построение байткода и классы символов живут внутри wasm. Затем текст копируется по адресу re_text_ptr(), и каждый re_match(len) прогоняет бэктрекинг-VM по уже скомпилированной программе. Модуль ничего не импортирует.

API

  • re_pattern_ptr() → i32 — буфер шаблона (4 КиБ);
  • re_text_ptr() → i32 — буфер текста (8 КиБ);
  • re_compile(len) → i32 — 0 при успехе, иначе код ошибки;
  • re_match(len) → i32 — 1 совпадение, 0 нет, −1 ошибка;
  • re_error(), re_error_pos() — код и байтовая позиция;
  • re_steps() — шагов VM в последнем поиске.

Синтаксис

Литералы, ., классы [...] и [^...] с диапазонами, \d \w \s, якоря ^ $, группы без захватов, альтернатива |, жадные * + ?. Флагов, захватов, {m,n} и ленивых квантификаторов нет. Поиск неякорный: движок пробует каждую стартовую позицию.

Коды ошибок

1 неожиданный символ, 2 незакрытая скобка, 3 лишняя скобка, 4 некорректный класс, 5 некорректный escape, 6 переполнение программы, 7 квантификатор не к месту, 8 лимит шагов, 9 шаблон длиннее 4 КиБ, 10 текст длиннее 8 КиБ, 11 шаблон не скомпилирован, 12 переполнение стека бэктрекинга.

Лимит в 1 000 000 шагов превращает катастрофический бэктрекинг в ошибку 8 вместо зависания. Это часть контракта, а не аварийный режим.

Реализации

  • re.wasm — ручной байткод (re.wat, собран через wasm-as);
  • re-rust.wasm, re-assemblyscript.wasm, re-c.wasm, re-cpp.wasm — Rust / AssemblyScript / C / C++; re-cpp-opt.wasm — тот же C++ с -O3.

Запуск

Ручная сборка встроена в страницу как base64, поэтому при открытии двойным щелчком работает и file://. Остальные движки загружаются через fetch: для них нужен локальный сервер, например python -m http.server.
